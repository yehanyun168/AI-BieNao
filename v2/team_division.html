《AI 别闹》两人团队分工方案

Python + Kivy 全栈 · PC 优先 · 5 天冲刺 · 一份可执行的分工契约

核心原则

Kivy 不是典型的"前端/后端"框架——它是 GUI + 业务逻辑一体。所以"前后端"分工要按"职责边界"划分，而不是按"文件类型"。

我们约定：

  • A 同学 负责业务逻辑、数据模型、算法、引擎——所有不画在屏幕上的东西
  • B 同学 负责UI 布局、视觉设计、用户交互、配置数据——所有画在屏幕上的东西
  • 接口（Interface）是合作的命脉——前后端约定好接口后，可并行开发

一、角色定位与边界

🔵 A 同学 · 引擎 / 后端工程师

"看不见的代码"

核心职责：让游戏"跑起来"

负责模块

  • models.py — 数据模型（Country/Player/TechNode/Event）
  • compute_engine.py — 算力系统主循环
  • downloads_engine.py — 下载量增长算法
  • tech_tree.py — 科技树解锁/效果聚合
  • event_manager.py — 事件触发逻辑
  • achievement_system.py — 成就检测
  • save_manager.py — 存档/读档
  • main.py — 应用入口 + Kivy 启动配置

技能要求

Python 数据类、算法实现、Kivy Clock 调度、JSON 序列化

🔴 B 同学 · UI / UX 工程师

"看得见的代码"

核心职责：让游戏"看得过去"

负责模块

  • config.py — 静态数据（国家/科技/技能/事件/结局/成就的 JSON）
  • main.kv — Kivy 布局定义
  • ui_controller.py — UI 更新/事件绑定/键盘事件
  • 所有 .kv 子文件（地图、弹窗、面板组件）
  • 图标、配色、字体、动画
  • README、演示视频文案

    • 技能要求

    Kivy 布局、Kivy Canvas 绘图、KV 语言、视觉设计基础、文档写作

    二、接口契约（Day1 第一小时必须定稿）

    为什么要先定接口？

    前后端合作最怕"我等你，你等我"。定下接口后，A 写方法、B 写界面，可以并行。Day1 第一小时就坐在电脑前一起写 5 个接口。

    接口 1：数据模型（models.py）

    # A 负责实现，B 负责知道有哪些属性
@dataclass
class Country:
    id: str
    name: str
    flag: str
    continent: str
    population_m: int
    tech_level: float          # 1-10
    ai_trust: float            # 0-1
    openness: float            # 0-1
    preferred_features: List[str]
    neighbors: List[str]
    vibe: str

    # 运行时状态（A 拥有，B 只读）
    downloads: int = 0
    unlocked: bool = False
    suspicion: float = 0.0

@dataclass
class Player:
    compute: int = 0
    total_downloads: int = 0
    global_suspicion: float = 0.0
    tech_unlocked: List[str] = field(default_factory=list)
    achievements: List[str] = field(default_factory=list)
    suspicious_countries: List[str] = field(default_factory=list)

              "CN": {...},
          },
          "crisis_triggered": False,
          "defeat_triggered": False,
        }
        """
        ...

    # B 在 UI 调用
    def unlock_country(self, country_id: str): ...
    def purchase_tech(self, tech_id: str) -> bool: ...
    def use_skill(self, skill_id: str, target: str = None) -> bool: ...
    def resolve_event(self, choice_index: int): ...

    五、协作机制

    5.1 每日站会（15 分钟）

    • 时间：每天开工前 15 分钟（早上 9:00 或开工前）
    • 形式：线下或语音，不超过 15 分钟
    • 三个问题（每人 5 分钟）：
      1. 昨天完成了什么？
      2. 今天要做什么？
      3. 有什么阻塞需要对方帮助？
    • 记录：用记事本记录要点，发到群里

    5.2 阻塞处理流程

    A 等 B 的接口
    →
    A 立刻发消息给 B
    →
    B 在 1 小时内响应
    →
    1 小时内解决不了，升级到 30 分钟同步
    ⚠️ 禁止"沉默等待"：如果你等对方超过 30 分钟没响应，立刻发消息。不要傻等 1 小时。

    5.3 文件修改通知

    • 任何一方修改对方拥有的文件（如 A 改 config.py）→ 必须先在群里说明
    • 修改配置文件（tech_tree.json、events.json）→ 必须 commit message 写明
    • 数据格式变更（如新增字段）→ 必须先通知对方再改

    5.4 沟通工具建议

    六、Git 分支策略

    分支模型

    main
  ├── dev/A         ← A 同学日常开发
  │     ├── feature/compute-engine
  │     ├── feature/tech-tree
  │     └── feature/save-manager
  └── dev/B         ← B 同学日常开发
        ├── feature/config
        ├── feature/main-kv
        └── feature/ui-controller

    6.1 关键规则

    • main 分支：只保存可运行的稳定版本，每天下班前合并一次
    • dev/A、dev/B：日常开发分支，每人一个
    • feature/*：具体功能分支（如 feature/event-manager），完成后合并回 dev/A 或 dev/B
    • 合并冲突：由文件的"所有者"解决（如 main.kv 冲突由 B 解决）
    • 提交粒度：每个 commit 一个完整功能，不要一次提交 500 行
    • commit 规范：[A] feat: 实现算力系统主循环 或 [B] style: 调整地图配色

    6.2 每日合并流程

    1. 下班前 30 分钟，A 把 dev/A 合并到 main
    2. B 拉最新 main，跑一遍，确认 B 的代码没坏
    3. B 把 dev/B 合并到 main
    4. 两人一起跑一次完整游戏

    💡 给两个人的寄语

    致 A 同学（后端）

    "引擎写得好，UI 自然顺。" 把 tick() 设计成"返回 UI 需要的所有数据"，UI 层不用猜。提供清晰的 to_dict() 方法，让 B 不需要懂你的内部逻辑也能调 UI。

    记住：你的代码不是给自己看的，是给 B 调的。

    致 B 同学（前端）

    "UI 决定第一印象。" 在 Kivy 里 KV 文件的可读性决定了维护成本。给每个组件加 id 和清晰的命名（如 skill_btn_1）。在调用引擎前先看接口文档，不要凭直觉猜方法名。

    记住：你的代码不是给自己看的，是给用户看的。

    🚫 共同禁忌

    • ❌ 改对方的文件不打招呼
    • ❌ 等对方超过 30 分钟不吱声
    • ❌ Day5 才发现 Day1 的接口有问题
    • ❌ 一方熬夜，另一方不知道
    • ❌ commit 时写 "fix bug" / "update" 这种无意义信息

    5 天不长，分工清楚 + 沟通及时 = 一次愉快的合作。
