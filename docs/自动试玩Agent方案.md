# 自动试玩 Agent 方案（补强 M1 测试力量）

> 背景：真人试玩数量少（M1 目标 ≥3 人尚未达成），希望用 agent 补充测试力量、
> 扩大覆盖、提升发现问题效率。本文回答三件事：有没有现成的、怎么建、缺什么条件。

---

## 一、现状确认：没有现成的"游戏试玩 agent"

**本会话可用的 agent 盘点：**

| Agent | 定位 | 能否当试玩用 |
|---|---|---|
| general-purpose / Explore / Plan | 通用编码、代码库探索、方案设计 | ❌ 能写测试代码，但不会"玩游戏" |
| sheet-agent / doc 系列 | 表格与文档处理 | ❌ 无关 |
| **quality-lead**（game-development-studio 专家包） | 游戏 QA：测试策略、测试计划、用例编写、冒烟/回归评审、bug 报告分诊、**playtest 报告评审** | ⚠️ 最接近，但是**规划评审型** |

- **quality-lead 功能范围**：产出 QA 策略/测试计划/用例清单，评审测试证据与试玩报告，做 bug 分诊。
- **适用场景**：设计测试矩阵、评审 agent/真人的试玩产出、规划回归范围。
- **调用方式**：Agent 工具 `subagent_type="quality-lead"`（本会话可直接调用），或在团队协作中作为 QA 角色派工。
- **关键局限**：它是"QA 总监"，只产出计划与评审意见，**不会自己启动游戏、模拟操作、跑流程记 bug**。

**结论：执行型试玩 agent（模拟玩家操作 / 自动探索流程 / 记录 bug）不存在，需要自建。**
但项目已有自动化资产可复用约 70%，自建成本比想象低（见下）。

## 三、方案：三层自动试玩 Agent

**定位与分工**：agent 补"覆盖 × 效率 × 稳定性"，真人补"手感 × 乐趣 × 可读性"。
agent **不评价好不好玩**，只回答三件事：**崩没崩（稳定）、对不对（数值/逻辑）、走得完吗（覆盖）**。

### L1 引擎层（无头批量试玩）—— 复用度最高，优先做

- **模拟玩家操作**：`auto_play` 驱动整局 tick 循环，策略脚本代替玩家做决策。
- **自动探索流程**：
  - 结局覆盖矩阵：7 结局 × 策略（default / compliance / 全技能流 / 速通流 / 挂机流）× 难度（easy/normal/hard），每组合 ≥200 局（结局分布结论需 ≥200 局，30 局只配回归）；
  - 分支遍历：6 技能、6 科技槽 × 18 分支全解锁路径、6 类委托模板全触发、危机选项三分支。
- **发现并记录 bug**（不变量断言 + 异常检测）：
  - 数值异常：NaN / 负值 / 越界（怀疑度、算力、下载）；
  - 卡死：连续 N tick 无状态进展；
  - 必输局：提前判定"该 seed 下无论怎么玩都关停"（不可玩状态）；
  - 结局触发与 report 透传不一致；委托结算/反制 clamp 异常。
- **记录格式**：每条异常 = `(seed, difficulty, strategy, tick, 状态快照, 断言名)` → 一键复现包 + 汇总报告（对齐 `docs/试玩报告模板.md` 的 Bug 表结构）。

### L2 UI 层（构建 + 事件注入 + 截图）—— 抓"渲染/接线"类隐性 bug

- **模拟玩家操作**：Kivy 构建真实界面（沿 test_v4_app 模式），**widget 级事件注入**模拟点击
  （按钮 / 页签 / 地图选国 / 科技升级），非真鼠标坐标。
- **检测目标**：布局异常（典型教训：P1-6 HudBox 子级画在 (0,0) 被技能带盖死，
  当时所有测试全绿——注入 + 控件位置断言正是抓这类 bug 的手段）、状态不同步、文案缺失、点击无响应。
- **环境约束**：⚠️ 必须默认窗口提供者（`KIVY_WINDOW=off` 会在 import 期崩），
  因此 L2/L3 只能跑在有桌面的机器（本机可跑，不能无头 CI）。

### L3 整包层（exe 冒烟 / 长跑）—— 发包前守门

- **流程**：启动打包 exe → 12s 冒烟（已有）→ 自动化走流程 1-2 小时长跑 → 采集 crash.log / fps / 进程内存曲线。
- **检测目标**：打包资源遗漏（缺文件即崩）、DLL 依赖、长时间内存泄漏、卡顿劣化。

### 落地形态（WorkBuddy 内）

1. `tools/playtest_agent.py`：L1/L2 执行器，输出 JSON 明细 + md 汇总报告；
2. 项目级自定义 agent `.workbuddy/agents/playtest-agent.md`：固化角色与工作流
   （跑矩阵 → 汇总异常 → 生成报告 → 按优先级排序），之后任意会话一句话调用"跑一轮自动试玩"；
3. （可选）夜间 automation：每天凌晨自动跑 L1 快速档（50 局）+ 晨间报告。

## 四、实现所需条件与待确认信息

| # | 条件/信息 | 说明 | 默认建议 |
|---|---|---|---|
| 1 | **策略脚本化** | 现 AUTO 深度优先有局限（P1-2 待修、合规之王可达率偏低）；探索不同结局需要 3-5 个目标明确的脚本策略，这是引擎层工作（约 0.5-1 人日/个） | 先做 default/compliance/挂机 3 个，够覆盖多数路径 |
| 2 | **异常判定标准** | 什么算 bug 的阈值表：怀疑度增长率上限、"卡死"的无进展周期数、必输判定的提前量 | 我按 TUNE 数值推导一版给你过目确认 |
| 3 | **UI 自动化深度** | widget 注入（稳、推荐、无新依赖） vs 真鼠标坐标（需 pyautogui/pywinauto，脆） | widget 注入 + 截图留档；真鼠标仅 L3 冒烟用 |
| 4 | **运行环境** | L2/L3 需桌面会话；跑批时段需避开你用机 | 夜间/后台时段跑 |
| 5 | **基线建立** | 需先跑一版"agent 基线"（各组合 200 局分布），之后所有改动对基线回归 | 随 M0 一起产出 |
| 6 | **真人/agent 报告分工** | agent 只代填客观项：基本环境、流畅度采样、Bug 表、客观难度；主观项（乐趣/手感/可读性/建议）留真人 | 模板 P0/P1/P2 已天然分层，可直接映射 |
| 7 | **成本预估** | L1 200 局无头约数分钟（单局毫秒级）；L2 单轮 1-2 分钟；L3 长跑 1-2 小时 | M0 先行验证实际耗时 |
