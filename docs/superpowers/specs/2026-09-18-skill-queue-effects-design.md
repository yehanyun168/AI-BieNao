# 技能连招、持续效果与存档契约：设计规格

**状态：**核心玩法、存档及验收边界已在对话中逐段获用户确认；一次性怀疑度与软上限的先后顺序作为下文标注的细节，待用户复核本文后编写实施计划。
**基线：**从 `codex/locked-country-economy` 的 `93f383d` 创建独立分支 `codex/skill-queue-effects`；锁国修复尚未合并主线，旧 A 工作树尚有未提交改动。
**范围：**修复技能已扣费却被覆盖、标示持续 2/3 周期却只生效 1 周期、存读档丢失已付费待结算效果；支持同周期不同技能连招。危机节奏调参、完整可信数值预览、开场动画及发行构建另立优化包。

## 问题与产品决定

`demo/engine.py` 当前只保留一个 `pending_skill` 和一份目标。`use_skill` 成功时已扣费、设冷却和记使用次数，再次施放会覆盖前一笔；`tick_one_round` 只消费最后一笔。`demo/ui_input.py` 还显式向 tick 传单个技能，形成第二真源。`Skill.duration` 仅声明而未参与结算；`save_manager.py` 保存冷却和计次，却未保存 pending。全局投放的一次性增量在现实现中还可能随已解锁国家数重复计算。

用户已选择：同周期允许多笔不同技能，**下一周期全部按施放顺序结算**；一次性算力/怀疑度增量在全局投放时每笔仅算一次，精准投放时每个有效目标算一次。不能继续维持“后施放覆盖先施放”、让一笔已收费技能无故延期到再下一周期，或保留全局重复增量。

## 不变量与状态生命周期

1. `PlayerState.skill_queue` 是有序待结算列表；每项保存技能 ID 和规范化的目标代码列表，空列表表示全局。`PlayerState.active_skill_effects` 保存已激活、仍将跨周期生效的技能 ID、目标和剩余结算周期。引擎是唯一真源；UI 不再持有可覆盖引擎的 `selected_skill`，也不再给 `tick_one_round` 传一个额外技能。现有 `skill_in_use` 显式参数应删除，或在过渡期对非空值明确报错，不能形成第二条隐式结算路径。
2. `use_skill` 保持现有调用入口，但成功后向队列追加一笔，而非覆盖单槽。扣费、冷却和 `skill_uses` 只在原子校验通过后立即发生；委托的技能使用计数仍以成功施放为准。不同技能可以连招；同技能在当前技能表中由冷却自然阻止重复施放。
3. 每个 tick 开始时固定本次队列快照，按入队顺序将所有预约转为本次生效项。本次新项和上周期尚有效项都参与本周期结算；本次之后才预约的技能留到下一 tick。引擎报告按 FIFO 记录激活项，便于 UI 日志与测试核对。正常情况下单笔只激活一次、不会丢失或重复执行。
4. `duration=d` 包括首次结算周期。每次结算末同时递减有效项的剩余周期和对应冷却，并在状态发布/存档前移除到期项。持续 1/2/3 周期的技能恰好参与 1/2/3 次结算；一次性 `compute_delta`、`suspicion_delta` 只在从队列激活的首次结算触发，绝不在后续持续周期重放。
5. 技能设计的硬约束是**非 bool 整数且 `1 <= duration <= cooldown`**。现有 10 个技能均符合。新技能不符合即数据校验失败，不作静默夹取；`duration=cooldown` 时二者在同一次 tick 末同步归零，先移除到期效果再发布可施放状态。任一稳定状态必须满足：同技能有效期间其冷却 `>0`，同一 ID 不得同时出现在队列与 active 中。运行时若发现违反不变量，应阻止本次状态转移并记录诊断，不能悄悄删除已付费效果。

## 效果组合与目标语义

- 每个国家只受全局施放或目标列表包含自身的技能影响。适用的下载、偷算力、怀疑增长及偷算力比例倍率按各笔相乘；固定比例加成按各笔相加，沿现有“先加、再乘、最后封顶”顺序计算偷算力比例。不同技能对同一国家可叠加；冷却—持续不变量排除同一技能的自我叠加。
- 一次性 `compute_delta` 和 `suspicion_delta` 不随持续时间重复。空目标全局投放每笔计算一次；精准投放按去重后的有效目标数计算，费用也按此目标数线性计算。**待书面复核的数值细节：**怀疑增长先按现有软上限聚合；技能说明中“怀疑度 +N%”的一次性增量随后按约定次数加入，最终怀疑度夹到 `[0,100]`。这样“+N%”不会被增长软上限吞掉；它有意修正旧全局重复计数，也可能改变精准投放的结果，必须在矩阵报告中单列。
- 保留科技、封锁折扣、国家解锁、事件和结局的既有阶段顺序；不因本包重写完整数值管线。预览和结算不能在连招口径上作相互矛盾的精确承诺。

## 预约校验与失败行为

引擎在写入任何费用、冷却、计数或队列项前，完整验证：游戏可继续、技能存在且已解锁、冷却为零、算力足额；目标输入格式合法、去重后的每个代码存在且按现有 `target_availability` 规则可投（已解锁且未达不可投阈值）。被政府阻止但仍可投的目标沿现有折扣语义处理。任一验证失败时四项状态均不变，UI 取得明确失败原因而非一律报“算力不足”。

成功预约时锁定技能和目标，不在下一 tick 因目标自然渗透变化而抹掉已付费预约或暗中退款；后续实际收益仍受当时经济状态、上限与阻止影响。全局空目标按一份收费。UI 与自动玩家均只走同一 `use_skill` 入口。

## 存档 v5→v6 与界面

- `SAVE_VERSION` 升为 6；v6 按顺序保存队列与 active 项的剩余周期。加载时先完整校验结构、技能 ID、目标、重复 ID、剩余周期和冷却一致性，失败返回现有坏档原因且保留加载前状态，不写回磁盘。保存只在现有正常保存路径发生。
- v5 及更早档逐级迁移，补空队列和空 active。旧版本从未保存 pending，无法推断究竟哪笔技能已付费却尚未结算；不伪造补偿、效果或退款，并在兼容性说明中告知。已存在的冷却、计次、结局和成就沿现有迁移规则保留。
- UI 用引擎状态显示有序“下周期结算”列表和持续效果剩余周期；读档、暂停/继续、回主菜单再进入后均从引擎重建。中英文文案都要说明预约与实际生效的时间。去掉单技能显式传参双真源。
- 现有 `preview_skill`、`preview_next_cycle` 的精确增量未覆盖多笔队列/active 时，不再作为 UI 的精确承诺；本包只保留可信的费用、冷却、目标可投性和技能效果文字。完整确定性预览与 tick 同源重构留给后续独立包；旧 A 工作树的相关改动只能定向移植，不能整体覆盖本分支。
