## 三、重要发现（比修复本身更值钱）

1. **P1-1 实测后回退（最有价值的负结果）**
   同种子 200 局前后对比：解锁门控单独 → 关停 26%→35.5%；教学事件单独 → 37.0%。且灵敏度 ×2 只把首危机从 42.0 挪到 41.8（不影响"何时爆发"，只影响命中率，代价关停 33.5→46.5%）。
   **结论：前段压力倒挂需要新机制（前段"新奇效应"热度项 / 下调 block_threshold），不是调参问题，建议立项。**

2. **30 局官方基线不具统计意义**
   基线 30 局：关停 16.7% / 渗透 37.95%；200 局实际：**26.0% / 33.91%**。30 局对 1~10% 的结局占比无分辨力（Poisson）。
   → 以后结局分布结论必须 ≥200 局；30 局只用作"逐位回归"。**此口径应写进 CONTRIBUTING。**

3. **两处"全绿但无效"的测试盲区被补上**
   - `test_v4_app` 只构建 widget 树、不断言最终位置 → HudBox 子级画在 (0,0) 被技能带盖死，**页签/委托条/预览条/投放三件套从未真正渲染上屏**（P1-6 修复）
   - `test_v4_app` 不做 tick 推进 → `MK['up']`/`MK['dn']`（不存在的键）潜伏崩溃漏网（P1-3 压测首跑抓到修复）

4. **两次 git 事故（环境级风险，需你知晓）**
   - 我用 `git stash` 对比基线时 `.git` 整个消失（与 09-11 同类的文件系统抽风）→ `git init + fetch + reset --mixed FETCH_HEAD` 完全恢复，零数据丢失
   - P2 子代理再用 stash → 5 个本地提交对象丢失且无 dangling 可捞 → 逐项内容抽查确认全在工作区后合并为一个提交重新落盘
   - **教训：这台机器上禁用 `git stash`**，对比基线改用只读的 `git archive` 导副本（本轮已验证此法可靠）

5. **性能真数据**：空闲/×1 推进 ~48fps 健康；高压（×4 速+抽屉）仅 10–22fps、p95 215ms（核显 2520×1470）。`ui_v4_screens.py` 每 tick 重建 ~120 控件是头号嫌疑，**有了 perf.log 这下可以定位了**。
